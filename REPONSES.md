Questions TP1
Question 1 : Lancez la commande symfony check:requirements. Listez les éventuels avertissements (warnings) affichés et expliquez leur impact.Rôle de la commande : Elle vérifie si votre environnement (PHP, extensions, outils) respecte les prérequis pour faire tourner Symfony correctement. Avertissements / impact : S'il y a des avertissements (par exemple une extension optionnelle manquante ou une configuration PHP non optimale), ils n'empêchent pas forcément le démarrage simple, mais ils peuvent limiter certaines fonctionnalités (comme l'internationalisation, le traitement d'images, la connexion base de données ou les performances) ou poser problème en production. (Si tout est vert/OK, aucun blocage majeur n'est signalé.)
Question 2 : Quel est le rôle du dossier public/ ? Pourquoi le fichier index.php se trouve-t-il dans ce dossier ?Rôle de public/ : C'est le dossier racine accessible depuis le web (il contient les fichiers publics comme les images, CSS, JS et le point d'entrée). Pourquoi index.php y est : C'est le point d'entrée unique (front controller) de l'application : toutes les requêtes HTTP passent par index.php pour charger Symfony, au lieu d'exposer directement les fichiers internes (src/, config/, .env).
Question 3 : Ouvrez le fichier .env à la racine du projet. Quelle variable d'environnement contrôle le mode de l'application (développement/production) ?C'est la variable APP_ENV (par exemple APP_ENV=dev pour le développement, APP_ENV=prod pour la production).
Question 4 : Que se passe-t-il si vous accédez à /profil/abc ? Pourquoi ?Symfony renvoie une erreur 404 (Not Found).Pourquoi : La route /profil/{id} a une contrainte requirements: ['id' => '\d+'], ce qui exige uniquement des chiffres (0-9). Comme abc ne correspond pas à un nombre, la route ne matche pas.
Question 5 : Combien de routes sont actuellement définies dans votre application ? Identifiez celles que vous avez créées et celles fournies par Symfony (debug, profiler…).Le nombre exact dépend des routes créées et de l'environnement (dev), et s'affiche avec php bin/console debug:router. Vos routes : Celles définies dans vos contrôleurs (ex. app_accueil, app_bonjour, app_profil, app_articles, app_article_nouveau, app_article_detail, etc.). Routes Symfony : Les routes internes fournies automatiquement en mode dev pour le débogage et le profiler (ex. \_profiler, \_wdt, \_error, etc.).
Question 6 : Expliquez le rôle de loop.index dans la boucle {% for %}. Quelle est la différence avec loop.index0 ?loop.index : Donne le numéro de l'itération en cours en commençant à 1 (1, 2, 3…).loop.index0 : Donne le numéro de l'itération en cours en commençant à 0 (0, 1, 2…), comme l'index d'un tableau classique.
Question 7 : Ouvrez le fichier de migration généré dans migrations/. Quelle requête SQL y est contenue ? Que fait-elle ?Elle contient principalement une requête CREATE TABLE article (...) (avec les colonnes id, titre, contenu, auteur, date_creation, publie et la clé primaire).Ce qu'elle fait : Elle crée la table article dans la base de données pour correspondre à l'entité Article.
Question 8 : Qu'est-ce que le ParamConverter ? Quel avantage apporte-t-il par rapport à une recherche manuelle via le Repository ?ParamConverter (résolution automatique d'argument) : C'est le mécanisme de Symfony qui convertit automatiquement un paramètre de l'URL (comme {id}) en un objet entité (ex. Article $article).Avantage : Il évite d'écrire manuellement $articleRepository->find($id) et la vérification if (!$article) { throw $this->createNotFoundException(); }, car Symfony le fait automatiquement et retourne une 404 si l'entité n'existe pas.

Question 1 : Quel est l'avantage de créer un FormType dans une classe séparée plutôt que de construire le formulaire directement dans le contrôleur ?
Cela garde le contrôleur léger et propre (il ne gère pas les détails du formulaire).
Cela permet de réutiliser le même formulaire dans plusieurs endroits (par exemple pour créer et pour modifier un article) et de le modifier facilement en un seul endroit.
Question 2 : Expliquez le cycle de vie d'un formulaire Symfony : que se passe-t-il entre l'affichage du formulaire vide et l'enregistrement en base de données ?
Affichage : Le contrôleur crée le formulaire lié à l'objet (ex. Article) et l'envoie à Twig pour afficher le formulaire vide.
Soumission (handleRequest) : Quand l'utilisateur envoie le formulaire, Symfony récupère les données de la requête et remplit l'objet Article.
Validation (isValid) : Symfony vérifie que les données respectent les règles (Assert\...) définies sur l'entité ou le formulaire.
Enregistrement (persist + flush) : Si tout est valide, on prépare et on enregistre l'objet dans la base de données.
Question 3 : Quelle est la différence entre form_row() et l'utilisation séparée de form_label() + form_widget() ? Dans quel cas préférer l'un ou l'autre ?
form_row() : Affiche en une seule fois le label, le champ et les éventuelles erreurs.
form_label() + form_widget() : Permet de placer le label et le champ séparément (et d'ajouter par exemple form_errors() où on veut).
Quand choisir : On préfère form_row() pour aller vite et garder un code simple ; on préfère form_label() + form_widget() quand on a besoin d'un design HTML/Bootstrap plus personnalisé.
Question 4 : Quelle est la différence entre la validation côté client (HTML5, JavaScript) et la validation côté serveur (Symfony Validator) ? Pourquoi est-il important de toujours valider côté serveur ?
Côté client : S'exécute dans le navigateur (ex. required, type="email", JS) pour donner un retour rapide à l'utilisateur.
Côté serveur : S'exécute sur le serveur PHP avec Symfony Validator avant d'enregistrer les données.
Pourquoi toujours valider côté serveur : Un utilisateur malveillant peut contourner le navigateur (désactiver JS, modifier le HTML ou envoyer une requête directement), donc seul le serveur garantit la sécurité et l'intégrité des données.
Question 5 : Ouvrez le fichier de migration généré. Quelle modification SQL a été ajoutée pour créer la relation ? Qu'est-ce qu'une clé étrangère ?
Modification SQL : L'ajout d'une colonne de liaison (ex. categorie_id) dans la table article et une contrainte de clé étrangère (FOREIGN KEY / ADD CONSTRAINT) qui la relie à la colonne id de la table categorie.
Clé étrangère : C'est une colonne dans une table qui fait référence à la clé primaire (id) d'une autre table afin de lier les deux tables et garder des données cohérentes.
Question 6 : Quels sont les avantages et inconvénients de createFormBuilder() par rapport à un FormType séparé (make:form) ?
createFormBuilder() : Pratique et rapide pour un formulaire simple et ponctuel directement dans un contrôleur, mais difficile à réutiliser ailleurs et il alourdit le contrôleur si le formulaire grandit.
FormType séparé (make:form) : Demande un fichier en plus, mais il est propre, réutilisable et mieux organisé pour les formulaires complets ou récurrents.
Question 7 : Pourquoi ne faut-il pas appeler persist() lors de la modification d'une entité existante ? Quel concept Doctrine explique ce comportement ?
Pourquoi : Parce que l'entité existe déjà en base et que Doctrine la suit déjà, donc flush() suffit pour enregistrer les changements.
Concept Doctrine : C'est le cycle de vie des entités et l'état géré (managed) par l'EntityManager (qui détecte automatiquement les modifications sur les entités gérées).
Question 8 : Qu'est-ce qu'une attaque CSRF ? Pourquoi est-il dangereux d'utiliser une simple requête GET pour supprimer une ressource ?
Attaque CSRF (Cross-Site Request Forgery) : Un site malveillant force le navigateur d'un utilisateur connecté à envoyer une requête à votre application à son insu en utilisant ses cookies/session actifs.
Danger de GET pour supprimer : Une requête GET est censée lire des données, pas modifier ou supprimer ; un simple lien ou une image <img> pointant vers l'URL de suppression pourrait déclencher la suppression automatiquement (par exemple via un clic ou un préchargement).

Question 1 : Qu'est-ce qu'un Password Hasher ? Pourquoi Symfony utilise-t-il l'algorithme auto par défaut ?Password Hasher : Il transforme le mot de passe en un code secret impossible à inverser avant de l'enregistrer en base, puis vérifie le mot de passe tapé à la connexion. Pourquoi auto ? Symfony choisit tout seul le meilleur algorithme sécurisé disponible sur votre version de PHP (comme bcrypt ou argon2), sans réglage compliqué.
Question 2 : À quoi sert la section providers ? Quel est le rôle du UserProvider dans Symfony ?Section providers : Elle dit à Symfony où trouver les utilisateurs (base de données, fichier, etc.).Rôle du UserProvider : Il charge l'utilisateur (User) à partir de son identifiant (comme l'email) lors de la connexion.
Question 3 : Dans RegistrationController, pourquoi utilise-t-on plainPassword au lieu de password directement pour le formulaire ? Quel est le risque si on stockait le mot de passe en clair ?Pourquoi plainPassword ? C'est un champ temporaire pour lire le mot de passe avant de le hacher ; password garde seulement la version hachée en base. Risque en clair : Si quelqu'un accède à la base de données, il voit directement tous les mots de passe des utilisateurs.
Question 4 : Qu'est-ce que l'objet app dans Twig ? D'où vient app.user ?Objet app : Une variable disponible partout dans Twig pour accéder aux infos utiles de l'application (utilisateur, messages flash, etc.). Origine de app.user : Elle vient de la sécurité Symfony : elle donne l'utilisateur connecté, ou null s'il n'est pas connecté.  
Question 5 : Quelle est la différence entre Authentification et Autorisation ?Authentification : Vérifier qui est l'utilisateur (ex. email + mot de passe).Autorisation : Vérifier ce qu'il a le droit de faire (ex. ROLE_USER ou ROLE_ADMIN).
Question 6 : Qu'est-ce que la Hiérarchie de rôles ? Comment configurer security.yaml pour que ROLE_ADMIN possède automatiquement les droits de ROLE_USER ?Hiérarchie de rôles : Un rôle supérieur récupère automatiquement les droits des rôles en dessous. Configuration dans config/packages/security.yaml :YAMLsecurity:
role_hierarchy:
ROLE_ADMIN: ROLE_USER
Ainsi, ROLE_ADMIN a aussi les droits de ROLE_USER.

Question 2 : Pourquoi est-il préférable d'utiliser setParameter() plutôt que de concaténer directement une variable dans la requête ? (Concept de JS Injection / SQL Injection)Avec setParameter() : La valeur est envoyée séparément comme simple donnée, donc elle ne peut pas casser ou modifier la requête SQL.Avec la concaténation directe : Un texte malveillant collé dans la requête peut modifier la commande SQL (SQL Injection) ou injecter du code dans la page (JS Injection / XSS).
